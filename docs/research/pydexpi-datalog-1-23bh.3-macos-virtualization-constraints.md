# macOS virtualization packaging constraints

Bead: `pydexpi-datalog-1-23bh.3`

## Decision summary

Shipping an Apple Silicon VM substrate inside PortLog is **feasible in principle, but not with the current package or release configuration**. The supported product shape should remain a directly distributed, arm64-only Electron app outside the Mac App Store. App Sandbox is optional for Developer ID distribution, whereas Hardened Runtime, Developer ID signatures on every executable, secure timestamps, and notarization are release requirements. Apple requires the Hypervisor entitlement in the process that uses Hypervisor APIs. [Apple distribution guidance](https://developer.apple.com/documentation/xcode/preparing-your-app-for-distribution) [Apple notarization requirements](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution) [Hypervisor entitlement](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.security.hypervisor)

The current PortLog builder configuration is development-only: it selects arm64 but uses ad-hoc signing, disables Hardened Runtime and strict verification, and excludes sidecar code from signing. That is a **hard blocker for public distribution**, not evidence that virtualization cannot ship. QEMU is the only backend exercised by the prior prototype. `krun` offers a much smaller native surface but does not remove signing, entitlement, image, licensing, or packaged-runtime proof obligations.

## Evidence boundary

The `.5` prototype established that unmodified VMPI 0.4.1, Gondolin 0.10.0, and Homebrew QEMU 11.0.3 can set up, resume, execute a native child, enforce the observed network policy, and cancel on this arm64 workstation when VM memory is raised to 2 GiB. It did **not** run from a copied, Developer-ID-signed, hardened, notarized `.app`; QEMU and all of its libraries came from `/opt/homebrew`. The present report therefore treats that result only as executable development evidence.

No packaged-app virtualization proof exists yet. In particular, no clean Sonoma machine without Homebrew has launched a notarized PortLog build, exercised either backend, verified nested signatures and entitlements, or completed first-run image creation/download. Those are release-gate unknowns.

## Constraint matrix

| Area | Classification | Constraint and consequence |
|---|---|---|
| Product architecture | Requirement | PortLog is already arm64-only with a macOS 14 minimum. Gondolin maps Node `arm64` to an AArch64 guest; QEMU supports HVF on macOS Arm, while krun requires guest and host architecture to match. Do not claim x64, Universal, or Rosetta support. [QEMU accelerator matrix](https://www.qemu.org/docs/master/system/introduction.html) [Gondolin backend checks](https://github.com/earendil-works/gondolin/blob/29fa74d802112f29c720990aced26165e0d57d84/src/sandbox/server-options.ts) |
| App Store / sandbox | Requirement | Use direct Developer ID distribution, not MAS. Apple requires App Sandbox for the Mac App Store but makes it optional for notarized direct distribution; Electron also states that the normal Darwin build is not an App-Sandbox build. PortLog's current local project, child-process, and loopback model therefore need not be redesigned around MAS sandbox rules for this target. [Apple App Sandbox](https://developer.apple.com/documentation/security/app-sandbox) [Electron MAS guide](https://www.electronjs.org/docs/latest/tutorial/mac-app-store-submission-guide/) |
| Signing and notarization | **Hard blocker in current config** | Replace ad-hoc identity with Developer ID Application, enable Hardened Runtime, remove signing exclusions, use secure timestamps, sign all nested Mach-O executables/dylibs, submit with `notarytool` or electron-builder notarization, inspect the notary log, staple, then verify with `codesign`, `spctl`, and stapler. Apple explicitly rejects ad-hoc/non-Developer-ID or unhardened submissions. [Apple notarization requirements](https://developer.apple.com/documentation/security/notarizing-macos-software-before-distribution) [electron-builder mac signing](https://www.electron.build/docs/features/code-signing/code-signing-mac/) |
| Electron entitlements | Requirement | Electron/V8 needs an Electron-compatible hardened-runtime entitlement set; this must be explicit and verified in the signed product rather than inferred from the packaging tool. Grant virtualization separately to the actual VMM child. Avoid `get-task-allow`; do not add `disable-library-validation` unless a measured nested-library failure proves it necessary, because Apple describes library validation as a protection and recommends exceptions only where needed. [electron-builder mac configuration](https://www.electron.build/mac/) [Apple common notarization issues](https://developer.apple.com/documentation/security/resolving-common-notarization-issues) |
| Hypervisor entitlement | Requirement | `com.apple.security.hypervisor=true` is required in **every process that calls Hypervisor APIs**. For QEMU/HVF that means `qemu-system-aarch64`; for krun it means `gondolin-krun-runner`. Adding it only to Electron main or an inherited helper plist is insufficient unless that executable is actually the caller. PortLog targets macOS 14, so the deprecated pre-10.15 companion entitlement is unnecessary. [Apple entitlement definition](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.security.hypervisor) |
| Nested code layout | Requirement | Keep command tools and dylibs outside ASAR, preferably in a conventional nested-code location or a carefully staged `extraResources` tree. Apple warns that nonstandard layouts can cause signing/distribution failures; nested helpers and libraries have their own signatures and are sealed by the outer app. The app bundle must remain read-only at runtime. [Apple nonstandard-code guidance](https://developer.apple.com/documentation/xcode/embedding-nonstandard-code-structures-in-a-bundle) [Apple code-signature structure](https://developer.apple.com/library/archive/documentation/Security/Conceptual/CodeSigningGuide/AboutCS/AboutCS.html) [electron-builder contents](https://www.electron.build/docs/contents/) |
| First-run installation | **Hard blocker if host prerequisites remain** | A public PortLog release cannot assume `brew install qemu`, Node, npm, root privileges, or build tools. VMPI currently documents QEMU as an external prerequisite and `setup` downloads Pi, installs guest packages, and creates a checkpoint. Either ship a complete signed backend and immutable base assets, or specify a checksum-pinned, resumable first-run download with clear consent, failure/retry/offline behavior, provenance, license delivery, and update policy. [VMPI README](https://github.com/JoshMock/the-agency/blob/b3742eea7afad8f6da8fe87a36efa1463d183af7/packages/vmpi/README.md) |
| Writable state | Requirement | Never create checkpoints, caches, downloaded images, temporary configs, or logs under `Contents/Resources`. Override VMPI's `~/.vmpi` and Gondolin's `~/.cache/gondolin/images` defaults into PortLog-owned paths derived from Electron `userData`/`cache`; use OS temporary storage for per-run scratch and delete it on terminal completion. Electron documents app-owned path APIs, and Apple treats the app bundle as read-only sealed content. [Electron `app` API](https://www.electronjs.org/docs/latest/api/app) [Apple bundle guidance](https://developer.apple.com/documentation/xcode/embedding-nonstandard-code-structures-in-a-bundle) |
| Isolation status | Requirement | A VM is not equivalent to App Sandbox. PortLog may remain unsandboxed while using a VM as the untrusted-command boundary. QEMU's own security policy recognizes AArch64 `virt` with a hardware accelerator such as HVF as a supported virtualization use case; TCG is classified as non-virtualization and must not be a silent security fallback. [QEMU security policy](https://www.qemu.org/docs/master/system/security.html) |

## QEMU packaging assessment

Gondolin's QEMU backend spawns a `qemu-system-*` child by path and selects `hvf` on same-architecture Darwin; QEMU itself says HVF supports macOS Arm and that TCG is the default when acceleration is not explicitly selected. The packaged adapter must pass an absolute `qemuPath`, require arm64/HVF, and fail closed if entitlement or accelerator initialization fails. It must not search the user's `PATH` or fall back to TCG. [Gondolin controller](https://github.com/earendil-works/gondolin/blob/29fa74d802112f29c720990aced26165e0d57d84/src/sandbox/controller.ts) [QEMU invocation](https://www.qemu.org/docs/master/system/qemu-manpage.html)

QEMU is not a single-file copy from Homebrew. The current Homebrew formula declares QEMU GPL-2.0-only and runtime dependencies including capstone, dtc, glib, GnuTLS, libpng, libslirp, libssh, libusb, pixman, and others. Local inspection of the tested arm64 bottle found direct `/opt/homebrew/opt/...` load commands and a 681 MiB Cellar installation. Homebrew proves availability and dependency shape, not that its relocations or signatures are suitable for embedding. Production therefore needs a PortLog-owned, version-pinned minimal arm64 build, only required system emulator/tools/resources, relocatable `@rpath`/bundle-relative dylibs, and a complete recursive dependency/license inventory. [Homebrew QEMU formula](https://github.com/Homebrew/homebrew-core/blob/HEAD/Formula/q/qemu.rb)

Every shipped Mach-O child and non-system dylib must be signed inside-out with PortLog's Developer ID and hardened runtime before the outer app is signed and notarized. Runtime assets needed by the selected build—such as modules, firmware/keymaps if referenced, guest kernel/rootfs, and checkpoint metadata—must be resolved from packaged resources or PortLog state, never Homebrew prefixes. Which files a minimized Gondolin command line actually needs is an **unknown requiring a clean-bundle trace**.

Redistribution is allowed only with compliance work. QEMU as a whole is GPLv2; binary distribution requires the GPL notice and complete corresponding source or a GPLv2-compliant written offer, including build/control scripts for the distributed executable. Bundled firmware and every dylib can have separate licenses, so they need their own notices and source/offer analysis. Mere aggregation does not by itself apply GPL to PortLog, but legal review should approve the precise bundle and source-delivery mechanism. [QEMU license statement](https://gitlab.com/qemu-project/qemu/-/blob/master/LICENSE) [GPLv2 terms shipped by QEMU](https://gitlab.com/qemu-project/qemu/-/blob/master/COPYING)

## Does krun change the picture?

Yes on payload shape; no on Apple's trust chain. Gondolin 0.10.0 publishes an optional Darwin-arm64 runner package containing an arm64 `gondolin-krun-runner` and `libkrun` dylib. Its source auto-detects that package, requires matching host/guest architecture and krun kernel/initrd assets, and rejects a macOS runner lacking the Hypervisor entitlement. [Gondolin README](https://github.com/earendil-works/gondolin/blob/29fa74d802112f29c720990aced26165e0d57d84/README.md) [runner resolution](https://github.com/earendil-works/gondolin/blob/29fa74d802112f29c720990aced26165e0d57d84/src/sandbox/server-options.ts) [entitlement check](https://github.com/earendil-works/gondolin/blob/29fa74d802112f29c720990aced26165e0d57d84/src/sandbox/krun-controller.ts)

Local package inspection found the published runner and dylib only ad-hoc signed; both must be re-signed and notarized as nested PortLog code while preserving the runner's hypervisor entitlement and valid `@rpath` resolution. Unlike the broad Homebrew QEMU graph, this is a compact, explicit native payload. However, krun remains an **unknown, not a selected replacement**: `.5` did not execute it; VMPI's setup/checkpoint behavior was tested only with QEMU; Gondolin documents backend-specific options and boot assets; and no hardened packaged Electron run has proved launch, mounts, networking, cancellation, or checkpoint compatibility.

Gondolin and its published runner package declare Apache-2.0, while `libkrun` is Apache-2.0. The krun boot/kernel material still carries separate obligations: `libkrunfw` states that its bundled Linux kernel is GPL-2.0-only and its library code LGPL-2.1-only, requiring corresponding source with binary distribution. Inventory the exact runner dylib and kernel/initrd provenance rather than relying only on the npm package's top-level license. [Gondolin license](https://github.com/earendil-works/gondolin/blob/29fa74d802112f29c720990aced26165e0d57d84/LICENSE) [libkrun](https://github.com/containers/libkrun) [libkrunfw licensing](https://github.com/containers/libkrunfw#license)

## Required release proof

Before either backend is production-eligible:

1. Build from a clean, pinned arm64 dependency graph and place every spawned native executable and dylib outside ASAR in the signed bundle.
2. Sign the VMM child with `com.apple.security.hypervisor`, sign its dylibs/helpers inside-out, sign Electron with only its required JIT entitlements, enable Hardened Runtime, and notarize/staple the final DMG.
3. Verify every nested signature and entitlement, dependency path, architecture, and notarization ticket; reject `/opt/homebrew`, source-checkout, unsigned, x64, TCG-fallback, and mutable-bundle references.
4. On a clean non-admin macOS 14+ Apple Silicon account with no Homebrew or developer tools, install from the stapled DMG and run setup, normal execution, isolation probes, cancellation, quit/relaunch, offline/error recovery, and state cleanup.
5. Ship complete third-party notices and a reviewed corresponding-source mechanism for QEMU or the krun/kernel payload actually distributed.

Until that proof exists, **QEMU packaging is requirement-heavy but technically plausible; krun is the preferable packaging experiment, not yet production evidence**. Neither constraint changes the prior Hybrid preference: Pi and PortLog capabilities can stay host-authorized while only the risky native command path enters the guest.
