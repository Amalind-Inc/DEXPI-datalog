# The models.dev Catalogue Is the BYOK Provider/Model Source of Truth

Which providers and models a reviewer may bring a key for is decided by a
vendored snapshot of [models.dev](https://models.dev) — the same catalogue pi
and opencode use — regenerated by `scripts/refresh_model_catalog.py` into
`pydexpi_datalog/llm/model_catalog.json`. Both the Python backend
(`model_catalog.py`) and the Next frontend (`byok-catalog.ts`) read that one
file, so the two cannot drift.

This replaces two hand-maintained tables in `model_access.py`:
`SUPPORTED_BYOK_PROVIDERS` (4 providers) and `NATIVE_TOOL_CAPABLE_MODELS` (an
exact provider/model allow-list of 6 pairs). Adding a provider is now a
catalogue refresh, not a code change. The catalogue currently yields ~150
providers and ~3,700 models.

**Capability gating moves into the snapshot.** models.dev records `tool_call`
per model; the generator keeps only models where it is true. Grounded QA drives
the model through native tool calls, so presence in the catalogue *is* the
capability check — one rule instead of an allow-list that silently went stale
as vendors shipped models.

**Three wire formats, not 150 integrations.** Providers are bucketed by the
adapter they need: OpenAI-compatible `/chat/completions` (the overwhelming
majority, including OpenRouter and every aggregator), Anthropic Messages, and
Gemini `generateContent`. A provider whose npm package implies anything else is
dropped by the generator rather than offered and then failed at request time.
That deliberately excludes AWS Bedrock (sigv4 signing), Azure OpenAI and Vertex
(multi-field auth and deployment routing), and bespoke vendor SDKs. Adding any
of them is a new adapter plus a config shape, not a catalogue entry.

**Rejected alternatives.** (1) Fetching models.dev at runtime, as some harnesses
do with a cache: an upstream edit could then change which models a review is
allowed to run, and the app would need the network to start. (2) Hand-curating
a broader list: that is the failure mode being removed. (3) A bare
"OpenAI-compatible base URL + key" escape hatch as the primary mechanism (the
Cursor approach): it works, but it gives up model metadata, tool-call
capability, and any picker better than a text field.

**Constraints the generator enforces.** A credential may only cross the network
over TLS; plaintext `http` is accepted solely for loopback endpoints, where
local model servers (LM Studio and friends) legitimately serve it and nothing
leaves the machine. A provider needing more than one credential value cannot be
configured from a single API-key field and is dropped. Models are ordered
newest-first because the picker defaults to the head of the list, and
alphabetical order would default a 273-model aggregator to whatever sorts first.

**Local servers are an overlay, not catalogue entries.** Ollama's endpoint and
model set belong to the operator's machine, so it is injected by both loaders
with open model membership — any model the operator has pulled is accepted.
Legacy provider ids are aliased (`gemini` → models.dev's `google`) so stored
keys and existing `.env` files keep working.

Governing related ADRs: 0014 (BYOK keys live in the browser — unchanged; this
ADR only widens *which* providers a browser-held key may name).
